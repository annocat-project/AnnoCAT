# Annotation result correctness validation

Status: Consequence, genotype, cache-format, and result-projection gates implemented; expanded Ensembl oracle exposes ten boundary failures
Last updated: 2026-08-15
Applies to: fastVEP output, local variant-annotation sources, OSA1 and OSA2
caches, result conversion, selected evidence, online FAVOR enrichment, result
queries, Variant Details, and export

AnnoCAT remains for research and educational use only. This plan verifies that
AnnoCAT faithfully applies its declared annotation sources and selection rules.
It cannot prove that an external assertion or predictor is biologically true.

## 1. Decision

AnnoCAT will use one small, versioned semantic validation corpus and one
end-to-end comparison harness. The corpus is coverage-driven: its size is the
smallest number of alleles needed to exercise every supported representation,
scope, source contract, and known failure mode. A target such as 200 or 500
variants is not an acceptance criterion.

Expected values must come from an independent, pinned source. They must not be
generated by AnnoCAT, fastVEP, an AnnoCAT cache, or the same parser that is being
tested.

Keep the existing `annocat results validate` command as an integrity check. Do
not turn it into a source-data validator and do not add semantic validation to
the normal result-open path.

The implementation has two lanes:

1. Pull-request validation uses one small public fixture bundle: input VCFs,
   schema-faithful synthetic source rows, and one independently authored
   expected-value file. A Rust integration test projects those expected records
   through AnnoCAT's canonical Parquet, query, filter, sort, and Variant Details
   paths.
2. The manual concordance workflow builds temporary OSA1 and OSA2 caches with
   the pinned fastVEP binary and requires both readers to reproduce the expected
   logical source records. Release validation additionally repeats source
   sampling against the actual installed caches and pinned raw source files
   under their applicable terms.

The temporary caches exercise production builders and readers; they do not
claim to represent a production source. Do not commit restricted source
content. Large managed caches are neither committed nor required in CI.
Expected values must remain independent even though the tiny caches are built
with production cache-building code.

The source fixture commits schema-faithful synthetic rows and an independent
expected-value file. The manual parity script covers exact OSA1/OSA2 source
records. The Rust comparator covers result conversion, representative
transcript selection, selected evidence, table queries, Variant Details,
filtering, sorting, and missing-versus-zero handling. Export remains covered by
the existing result-query tests; it is not yet asserted by this fixture.

The manual `Annotation concordance` workflow builds the fastVEP commit pinned
by AnnoCAT and annotates 196 public or synthetic reference-valid variants on
chromosomes 21, 22, X, Y, and MT with Ensembl 115 GFF3 and FASTA. It builds a
transcript cache from those same inputs and requires cache-backed annotation to
be byte-identical to direct-GFF annotation. It then submits the same VCF records
to Ensembl's release-pinned September 2025 REST archive and fails unless `/info/software`
reports release 115. The REST endpoint accepts at most 200 variants per POST,
so this public corpus fits in one request:
<https://sep2025.rest.ensembl.org/documentation/info/vep_region_post>.

The comparison requires exact multiset equality for every field with a direct
representation in both outputs. Missing variants, missing consequences,
duplicate-count differences, extra consequences, and mapped-field differences
fail the workflow. A versioned source-contract file can ignore only named
fields or allow named transcript identities, each with a reason. An unlisted
difference or a stale unused identity exception fails. The uploaded reproducibility
record contains the request, response, software-release response, tool
identity, contract identity, and SHA-256 hashes.

This lane does not compare VEP's `SOURCE`, `SYMBOL_SOURCE`, `HGNC_ID`, APPRIS,
or the paired RefSeq accession carried by VEP's `MANE_SELECT` field. The REST
response does not expose `SOURCE`; its Ensembl database supplies HGNC xrefs that
are absent from the chromosome GFF3 used by fastVEP; fastVEP's GFF3 loader does
not retain APPRIS; and AnnoCAT uses the Ensembl transcript plus the combined
MANE membership flag rather than the paired RefSeq accession. The lane compares
combined MANE membership, TSL, CCDS, protein ID, and the other mapped fields
listed in its JSON report. Fields excluded from this REST/GFF contract remain
unverified; AnnoCAT does not install or require VEP CLI to validate the fields
it supports. This proves consequence concordance only for the public corpus and
does not replace raw-source-to-cache validation.

## 2. What is and is not verified today

`annocat results validate` verifies declared SHA-256 hashes, readable result
tables, expected row counts, and required relations. These checks detect
missing, changed, and structurally invalid result files. They do not establish
that:

- an input allele was normalized to the correct genomic representation;
- evidence was joined to the correct alternate allele in a multiallelic record;
- a transcript vector was aligned to the correct transcript;
- a cache retained every duplicate source record;
- a missing value remained missing instead of becoming zero;
- the selected table value came from the same transcript shown in the table;
- Variant Details and export use the same resolved value; or
- a displayed score matches the pinned upstream source.

GIAB benchmarks validate variant-call handling, genotype concordance, resume
behavior, and WGS-scale performance. They are not annotation truth sets. NIST
also documents limitations involving difficult variants and equivalent complex
variant representations:
<https://www.nist.gov/programs-projects/faqs-genome-bottle>.

## 3. Correctness model

Validation is divided into boundaries. A value must pass every applicable
boundary; a final displayed match is insufficient because it does not identify
where an error entered.

### 3.1 Input allele to canonical result allele

Verify chromosome, position, reference, alternate, and reference-sequence
agreement independently for each alternate allele.

AnnoCAT's VCF contract uses reference-aware VCF normalization. Compare it with
`bcftools norm` using the exact same pinned GRCh38 FASTA. `bcftools norm`
left-aligns indels, checks REF alleles, and splits multiallelic records:
<https://samtools.github.io/bcftools/bcftools>.

GA4GH VRS identifiers may be recorded as an interoperability cross-check, but
they are not a coordinate oracle for AnnoCAT. VRS fully justified normalization
is not identical to conventional VCF left normalization. VRS is useful for
showing that independently represented alleles describe the same sequence
state:
<https://vrs.ga4gh.org/en/1.1/impl-guide/computed_identifiers.html>.

Required cases include:

- SNVs, insertions, deletions, MNVs, and symbolic or unsupported alleles;
- repeat-region indels with more than one valid VCF representation;
- multiallelic records containing mixed SNV and indel alternates;
- duplicate records and adjacent alleles;
- chromosomes 1-22, X, Y, and MT;
- accepted human alternate contigs and excluded decoy or viral contigs;
- reference mismatches and unknown bases; and
- called, partially called, and missing genotypes.

VCF `GT` allele-vector length declares the called ploidy. AnnoCAT preserves the
caller's `GT`, separator, and allele order; it does not infer sample sex or
rewrite ploidy from chromosome coordinates. Focused tests cover representative
diploid and haploid calls in X PAR and non-PAR labels, Y PAR and non-PAR labels,
MT haploid calls, and partially called genotypes. This proves faithful VCF-call
parsing, not sample-sex, karyotype, or ploidy QC. Those checks require declared
sample metadata and a separate QC contract. The VCF specification defines the
genotype encoding:
<https://samtools.github.io/hts-specs/VCFv4.5.pdf>.

PAR and mitochondrial consequence checks belong to the release-pinned Ensembl
oracle lane. They must not be inferred from genotype ploidy. Ensembl documents
the human pseudoautosomal regions separately from transcript consequence
generation:
<https://www.ensembl.org/info/genome/genebuild/human_PARS.html>.

### 3.2 Canonical allele to transcript consequences

Use Ensembl VEP as the independent consequence oracle. A local VEP comparison
must pin the binary, cache, FASTA, assembly, transcript source, and release to
the contract declared by the fastVEP build. Ensembl recommends matching the VEP
and cache releases:
<https://www.ensembl.org/info/docs/tools/vep/script/vep_cache.html>.

A release-pinned Ensembl REST archive is acceptable for fields that have a
direct JSON equivalent. Record `/info/software`, the exact request, the full
response, and their hashes. Never compare a current REST release with an older
fastVEP transcript model, and never infer parity for a field absent from the
REST response. Ensembl 115 was released in September 2025:
<https://www.ensembl.info/2025/09/02/ensembl-115-has-been-released/>.

Compare the complete supported consequence set for each allele, not only the
representative table consequence. VEP emits a separate prediction when an
allele overlaps more than one transcript:
<https://www.ensembl.org/info/docs/tools/vep/vep_formats.html>.

For each supported consequence, compare:

- stable gene ID and symbol;
- stable transcript or feature ID, including the declared version policy;
- all Sequence Ontology consequence terms, without keeping only the first;
- impact;
- biotype;
- exon and intron positions;
- HGVSc and HGVSp under the declared normalization options;
- canonical, MANE, APPRIS, transcript-support, CCDS, and protein identifiers;
  and
- representative allele-gene and table selection under
  `evidence-scope-resolution-architecture.md`.

Intentional fastVEP/VEP differences must be named by allele case, field,
expected value, observed value, reason, upstream reference, VEP and fastVEP
release, owner, and review date in a versioned exception file. Wildcards and
source-wide waivers are not allowed. A percentage agreement threshold must not
conceal an unexplained mismatch.

#### 3.2.1 fastVEP issue 81: protein in-frame indels

Issue 81 changes HGVSp nomenclature for protein in-frame insertions, deletions,
and deletion-insertions. It must not change consequence prediction, protein
coordinates, amino-acid fields, or ACMG evidence. The upstream acceptance
criteria are recorded in
<https://github.com/Huang-lab/fastVEP/issues/81>.

Full validation requires all of the following:

1. Use the 15 observed insertion cases named by the issue author. Record the
   genomic allele, transcript and release, raw protein position and amino-acid
   change, reference peptide, and expected Ensembl VEP HGVSp for each case.
   Test every case with and without peptide context. If this case table is not
   public, the issue author or upstream maintainer must run this gate; substitute
   examples do not prove that the original 15 cases pass.
2. Include independent branch coverage for a right-shifted duplication, a true
   insertion, a deletion, a deletion-insertion, a repeat-region shift, an
   incomplete-CDS peptide with leading `X`, a terminal `*`, a peptide mismatch,
   and a missing peptide. With peptide context, HGVSp must exactly match pinned
   Ensembl VEP. Without usable peptide context, output must remain an unshifted
   valid indel expression and must never become synonymous or missense.
3. Exercise both annotation call sites: the `fastvep-annotate` library path and
   the `fastvep-cli` VCF path. Both must pass `Transcript::peptide` to the HGVSp
   formatter without changing predictor-level protein coordinates or amino
   acids.
4. Run the same real-data VCF through the parent commit and candidate commit,
   and through Ensembl VEP CLI with the same release, cache, FASTA, transcript
   source, assembly, and HGVS options. Compare every transcript-level HGVSp and
   report before-and-after exact-match counts. The corpus must contain in-frame
   insertions; a general validation VCF with none cannot close this gate.
5. Run ACMG output on the same input before and after. The ordered multiset of
   allele, gene, transcript, consequence, `ACMG`, and `ACMG_CRITERIA` values must
   be byte-identical.
6. Require `cargo test --workspace`,
   `cargo clippy --workspace --all-targets -- -D warnings`, and
   `cargo fmt --check` to pass.

Current local validation used the public 343-allele corpus from
<https://github.com/Qnomx/fastVEP/pull/2>, its frozen Ensembl VEP oracle, the
clean parent commit, and the candidate implementation. That corpus now includes
all 15 insertion cases reported in issue 81. The candidate matched the expected
HGVSp for all 15 cases.

Among the 152 corpus records with an expected in-frame HGVSp comparison, the
parent commit had 17 exact matches, 118 differing values, one missing value,
and 16 malformed values. The candidate had 121 exact matches, 30 differing
values, one missing value, and no malformed values. It changed 133 values,
created 104 new exact matches, and regressed none of the parent's exact matches.
Focused tests cover both annotation call sites, peptide and no-peptide paths,
right-shifted duplication, insertion, deletion, deletion-insertion, repeat
shifting, leading `X`, terminal `*`, and unusable peptide context.

The parent and candidate produced the same 7,366 ordered ACMG rows. After only
the HGVSp field was blanked, every field in all 343 emitted VCF records was also
identical. Consequence terms, protein coordinates, amino-acid fields, and ACMG
evidence therefore remained unchanged in this corpus. `cargo test --workspace`
and `cargo fmt --all -- --check` pass.

The repository-wide strict Clippy gate is not yet green. The clean parent and
candidate both fail Rust 1.94 Clippy checks in code unrelated to issue 81; the
first shared failure is `Allele::from_str` in `fastvep-core`. No diagnostic is
reported in the issue 81 implementation file, `fastvep-hgvs/src/protein.rs`.
This inherited quality-gate failure must be fixed or explicitly waived before a
release can claim every gate in this section passed.

The frozen oracle proves the reported issue 81 formatter defect is fixed for
the public corpus. The separate SMARCA4 splice-boundary deletion is also fixed,
but in the shared transcript-aware nucleotide normalization layer rather than
in the issue 81 formatter. This preserves issue 81's blast-radius rule while
covering the previously missing HGVSp. The exact public REST checks and focused
unit tests are AnnoCAT's acceptance gate; VEP CLI is not a runtime, build, or CI
dependency.

Existing transcript caches remain readable and use the same format. A cache
built before the GFF parser fix can retain a fabricated protein-version suffix
such as `.1`; rebuilding that cache from the same pinned GFF3 and FASTA updates
the suffix without changing its schema. Existing result files are immutable and
must be reannotated to receive corrected HGVS text. CDS-completeness flags remain
outside the GFF3 source contract and are not inferred.

### 3.3 Raw source to cache

For every release-enabled local variant-annotation source, compare independently
parsed upstream records with lookups from the installed cache. Validate OSA1
and OSA2 separately when both formats are supported. Catalog-pending and
adapter-required sources enter this gate only when they become release-enabled.

The lookup key is the normalized genomic allele unless the source contract
explicitly declares another key. Matching only position is never sufficient.
GATK likewise describes external-resource annotation as requiring allele
concordance:
<https://gatk.broadinstitute.org/hc/en-us/articles/360050813772-VariantAnnotator>.

Required assertions:

- every expected source record is returned;
- no neighboring allele or alternate allele is returned;
- repeated exact-key records remain distinguishable until source-contract
  resolution is complete;
- the canonicalized logical multiset of source records is equal between raw,
  OSA1, and OSA2 representations before representative selection;
- multiallelic Number=A and Number=R fields select the correct alternate value;
- source missing markers remain missing;
- text, integer, identifier, and categorical fields are exact; and
- numeric fields are exact unless the cache contract declares a specific
  quantization rule.

The committed `fixtures/source-cache-parity` corpus implements this boundary
for the eight release-enabled supplementary adapters. The standard-library
script `scripts/verify-supplementary-cache-parity.py` builds both cache formats
with the pinned fastVEP binary, runs full cache verification, annotates the same
query alleles, and requires OSA1 and OSA2 to equal the independently authored
`expected.ndjson` exactly. The Rust result-projection test then verifies the
same expected records after conversion to canonical Parquet and through table,
filter, sort, and Variant Details queries.

A quantized field is checked twice:

1. raw source to cache must be within that field's declared bound; and
2. cache to result must be exact.

VCF `Number=A` values follow alternate-allele order. `Number=R` values contain
the reference first and then each alternate in ALT order. The GA4GH-maintained
VCF specification defines these rules:
<https://samtools.github.io/hts-specs/VCFv4.5.pdf>.

Do not use a generic floating-point epsilon across all fields. Any allowed
error must come from the pinned cache contract, record the quantization method,
and identify the affected field.

### 3.4 Cache to canonical result tables

Run the committed corpus through the release AnnoCAT binary with tiny caches
that use the same schemas and readers as a packaged release. Release validation
then repeats the test against actual installed caches. Read `variants.parquet`,
`consequences.parquet`, and `evidence.parquet` directly.

Assert that:

- each normalized alternate allele has the expected allele row;
- every supported raw transcript consequence is retained;
- allele-scoped evidence has no consequence identity;
- transcript-scoped evidence retains the correct consequence identity;
- selected scalar evidence points to the representative transcript or feature;
- missing values do not become zero, false, an empty string, or an empty JSON
  object;
- a selected scalar never becomes a range or concatenated transcript vector;
- source provenance and field paths identify the actual provider;
- dedicated local sources take precedence over duplicate copies only where the
  source catalog declares that policy; and
- a fresh run and a resumed run are semantically equal after row ordering is
  normalized. Binary Parquet hashes need not be equal.

Also open one small legacy-compatible result fixture without rewriting its
canonical files. Its page, detail, sort, filter, and export values must match
the same expected semantics.

### 3.5 Canonical tables to query and presentation

The backend is the semantic authority. For each tested field, verify that page,
sort, exact filter, text search, detail, and export use the same resolved value.

Presentation checks must distinguish the raw value from its formatted display:

- table and Variant Details receive the same raw value and provenance;
- sorting uses the raw typed value, not the rendered text;
- exact filtering uses the field's categorical normalizer;
- missing values sort and filter according to one declared policy;
- UI rounding does not alter the stored value;
- tooltips describe the same source, release, transcript scope, and
  interpretation policy as the value; and
- color and calibrated-evidence labels are tested separately from source-value
  assignment.

Reuse the existing Node presentation-policy tests. Do not duplicate the Rust
resolver in JavaScript test fixtures.

## 4. Source-specific requirements

### 4.1 ClinVar

Use the pinned NCBI release files, not the current ClinVar website, as the
oracle. Match the correct alternate allele before comparing variation
accession, germline classification, review status, conditions, and assertion
metadata.

Keep variant-level VCV aggregation separate from condition-level RCV or SCV
assertions. ClinVar documents that review status and classification are
calculated for different aggregate record types and exposed through distinct
release fields:
<https://www.ncbi.nlm.nih.gov/clinvar/docs/review_status/>.

### 4.2 dbSNP

Match the normalized allele before assigning a RefSNP identifier. Verify the
current rs ID, retired or merged IDs, exact assembly placement, and configured
allele-specific frequency metadata. A co-located allele is not sufficient.

The current RefSNP model reports alleles in the forward orientation of the
sequence on which they are placed:
<https://www.ncbi.nlm.nih.gov/core/assets/snp/docs/RefSNP_orientation_updates.pdf>.
NCBI also documents that a merged rs ID resolves to its current rs ID:
<https://www.ncbi.nlm.nih.gov/variation/view/faq/>.

### 4.3 gnomAD

Compare source release, dataset type, filter state, AC, AN, AF, homozygote
count, and each configured genetic ancestry group. Confirm the exact rule used
to calculate group maximum frequency.

AF is the alternate-allele count divided by the allele number. AN=0 means no
frequency information; it must not be displayed or stored as AF=0. gnomAD made
the same missing-versus-zero distinction in its browser:
<https://gnomad.broadinstitute.org/news/2023-08-modify-population-frequency-table/>.

Exome, genome, and combined frequencies are different contracts and must not be
substituted for one another.

### 4.4 dbNSFP and transcript-vector predictors

For each tested record, independently parse the raw dbNSFP row and preserve the
parallel transcript vectors. Verify:

- vector lengths and missing placeholders;
- Ensembl transcript ID to vector-index alignment;
- transcript IDs with and without versions;
- duplicate records for the same genomic allele;
- fields that are variant-level rather than transcript-level;
- selected transcript value for table, sort, filter, search, and summary; and
- values shown after the user changes transcripts in Variant Details.

The corpus must contain records where AlphaMissense, REVEL, SIFT, PolyPhen-2,
and other retained predictors differ between transcripts. A record whose
transcript values happen to be equal cannot validate transcript alignment.

### 4.5 SpliceAI

Compare the complete source tuple for each allele and gene:

`ALLELE|SYMBOL|DS_AG|DS_AL|DS_DG|DS_DL|DP_AG|DP_AL|DP_DG|DP_DL`.

The maximum delta score is the maximum of the four DS values from the same
source annotation record. DP values are signed positions relative to the
variant and are not scores. Variants overlapping multiple genes can have one
source record per gene, so any cross-record representative rule must be tested
explicitly. These semantics are documented by the SpliceAI project:
<https://github.com/Illumina/SpliceAI>.

### 4.6 CADD, phyloP, and other allele- or position-scoped scores

For CADD and other allele-scoped scores, compare the raw source value at the
exact normalized allele. For phyloP and other base-level tracks, compare the
value at the declared assembly and reference position. If the source contract
applies one position value to every alternate at that locus, test that behavior
explicitly and confirm that no adjacent position or reference base is used.

Test boundary values, negatives, zero, source missing markers, and values near
display and calibration thresholds.

Source assignment and evidence interpretation are separate tests. A correctly
assigned value may still have no approved calibrated interpretation.

### 4.7 Dedicated REVEL

REVEL is transcript-scoped in AnnoCAT. Match the normalized GRCh38 allele and
the transcript IDs declared by the pinned REVEL release before comparing the
score. Verify missense applicability, missing scores, transcript-version
normalization, and the value selected for table, sort, filter, search, summary,
and transcript changes in Variant Details.

The REVEL release files include Ensembl transcript IDs identifying the
transcript or transcripts to which an amino-acid substitution applies:
<https://sites.google.com/site/revelgenomics/downloads>.

### 4.8 FAVOR online annotations

FAVOR is a rolling service and does not provide an immutable release identifier
for every returned field. A live response therefore cannot serve as a
reproducible release oracle.

Use license-permitted frozen and redacted response fixtures, or schema-faithful
synthetic responses, to validate request batching, allele matching, response
parsing, field naming, missing values, and merge behavior. For a frozen
response, record endpoint, retrieval time, request contract, and response
SHA-256. Keep a live smoke test optional and non-blocking. It verifies
reachability and schema compatibility, not value reproducibility.

When FAVOR enrichment adds or replaces evidence, rerun the same query and
presentation invariants for the affected fields. Unrelated local values,
filters, selected genes, and transcript choices must remain unchanged.

## 5. Corpus construction

Construct the corpus by coverage matrix, then deduplicate alleles. Each row in
the matrix must have at least one positive case and, where meaningful, one
negative control.

Coverage dimensions are:

- allele representation;
- chromosome and contig policy;
- genotype state;
- gene overlap count;
- transcript count and selection rank;
- consequence type;
- source presence, absence, duplication, and conflict;
- biological scope: allele, gene, transcript, position, and source record;
- storage format: raw, OSA1, OSA2, Parquet, and online fixture;
- field type: text, identifier, category, integer, signed position, float,
  vector, and JSON;
- missing-value representation; and
- threshold and rounding boundary.

Include one small legacy result fixture. It validates compatibility only and is
not rewritten or used as a source oracle.

Add a deterministic, stratified release sample from each complete source to
detect common mapping errors outside the hand-curated matrix. The sample is a
release check, not a committed WGS fixture. Its seed, source hashes, selected
keys, and aggregate outcome are recorded without placing WGS row values in
review context.

## 6. Expected-value format

Use one line-oriented JSON or TSV file with explicit scope. A conceptual row is:

```text
assembly
chromosome
position
reference
alternate
normalized_allele_id
gene_id
transcript_or_feature_id
consequence_id
source_id
source_release
source_record_identity
cache_contract
field_path
raw_expected_value
cached_expected_value
value_type
allowed_raw_to_cache_error
quantization_method
provenance_reference
```

Use `null` for missing values. Do not encode missing as zero, an empty string,
or the word `Not reported`.

Expected UI text and color do not belong in this file. They remain in the
existing presentation-policy fixtures so a copy or theme change does not alter
the scientific oracle.

## 7. Acceptance gates

The validation corpus passes only when:

1. normalized allele identity agrees for every supported allele;
2. every expected supported consequence exists and no unsupported extra
   consequence is silently promoted;
3. every exact source field matches its independently extracted value;
4. every quantized source field stays within its declared field-specific raw
   bound and is exact after cache lookup;
5. no allele, transcript, or source record leaks into another allele or
   transcript;
6. no missing value becomes a biological zero;
7. selected transcript and selected evidence identities agree;
8. direct, selected, detail, query, and export values are semantically equal;
9. OSA1 and OSA2 produce the same logical source-record multiset and selected
   evidence for supported sources;
10. fresh and resumed annotations produce equivalent logical rows;
11. the legacy result fixture produces the same declared query and presentation
    semantics without modifying canonical files; and
12. every difference from the pinned independent oracle is either fixed or
    present in a narrow, reviewed, versioned exception entry.

There is no acceptable unexplained mismatch percentage. Aggregate agreement
rates may be reported, but they do not replace field-level gates.

## 8. Test cadence

### Pull requests

- Run the committed semantic source-contract corpus through the Rust result
  projection test.
- Run result integrity, resolver, and presentation-policy tests.
- Do not build fastVEP caches, require installed production caches, download
  large sources, or run live APIs.

### Release candidate

- Regenerate independent oracle outputs with pinned upstream tools.
- Build and verify the tiny OSA1/OSA2 source-contract caches.
- Run raw-to-cache comparisons against actual installed caches for every
  release-enabled source contract.
- Run OSA1/OSA2 equivalence where supported.
- Run the deterministic stratified source sample.
- Run the end-to-end corpus through the packaged release binary.

### Aggregate WGS release benchmark

- Use GIAB for call handling, throughput, memory, resume, and aggregate result
  invariants.
- Compare deterministic aggregate counts and sampled annotations.
- Do not use GIAB as evidence that external annotation values are correct.
- Do not emit WGS row values into logs, reports, or model context.

## 9. Reproducibility record

Every semantic validation report records:

- AnnoCAT version and commit;
- fastVEP version and commit;
- GRCh38 reference accession and SHA-256;
- transcript source, Ensembl release, and cache SHA-256;
- source IDs, releases, licenses, and content hashes;
- field-selection contracts and hashes;
- OSA format and converter version;
- normalization contract version;
- representative-selection contract version;
- evidence-calibration manifest hash;
- fixture version and oracle-generation commands;
- tiny cache-fixture hashes for CI or installed-cache hashes for release
  validation; and
- fresh, resumed, and online-fixture test outcomes.

This record proves which inputs and rules were tested. It does not imply that
the source assertions or computational predictions are true.

## 10. Implementation map

Reuse existing code and test surfaces:

- `crates/annocat-core/src/normalization.rs`: normalization unit cases;
- `crates/annocat-core/src/sample_call.rs`: VCF genotype and ploidy-preservation
  checks;
- `crates/annocat-cli/src/results.rs`: canonical table, evidence resolution,
  query, filter, sort, Variant Details, and source-parity projection assertions;
- `fixtures/source-cache-parity/`: raw synthetic source contracts and the

- `fixtures/fastvep/ensembl-115-xy-mt.vcf`: public-oracle X, Y, MT, and complex

- `config/dbnsfp-4.9a-curated-fields.json`: dbNSFP field and transcript

## 11. Non-goals

- Do not claim that a correct predictor value is pathogenic or benign.
- Do not validate source scientific accuracy by comparing two aggregators that
  copied the same upstream data.
- Do not use the current public website value when the installed source is an
  older pinned release.
- Do not accept coordinate-only source matches.
- Do not add semantic validation to result opening, sorting, or filtering.
- Do not rewrite existing results to run validation.
- Do not make a live FAVOR response a release gate.
- Do not require production annotation caches in pull-request CI.
- Do not use this plan to validate the scientific curation of assembly-independent
  phenotype, condition, gene-identity, or pathway knowledge caches. Those need
  separate source-contract tests.
- Do not store patient or private WGS variants in the public corpus.

## 12. Verification conclusion

This design is sufficient and minimal for AnnoCAT's current architecture. It
separates corruption detection from scientific data fidelity, uses independent
oracles, covers allele and transcript identity explicitly, and validates every
lossy or selecting transformation at the boundary where it occurs.

The implementation now includes an exact eight-source OSA1/OSA2 parity fixture,
a Rust end-to-end result-projection check, genotype-ploidy preservation tests,
an exact field-level VEP comparator, the expanded 196-record Ensembl workflow,
and the public GIAB CMRG sample. The next useful boundary is deterministic
sampling against complete installed release caches, plus a frozen online-source
fixture. Do not add a validation service, database, or WGS-sized golden result.
